# Журнал решений

Нетривиальные решения по проекту: что решили, почему, что отвергли. Новые записи —
**сверху**. Формат записи:

```
## D-NNN · YYYY-MM-DD · Заголовок
Статус: принято | предложено (ждёт владельца) | отменено (см. D-MMM)
```

`предложено` — значит решает владелец; агенты не считают это принятым.

## D-036 · 2026-10-19 · PDF сертификата на сервере: @react-pdf/renderer и статические срезы шрифтов
Статус: принято оркестратором; владелец может отменить
Решение. GET /[locale]/learn/[slug]/certificate/pdf рендерит PDF через @react-pdf/renderer
(пин 4.9.0, во встроенном списке serverExternalPackages Next 16) только для владельца
сертификата из сессии. Чужой или несуществующий — 404, гость — на вход. PDF не хранится:
ETag и `private, no-cache`, лимит 10 в минуту на пользователя. Шрифты — статические TTF-срезы
из вариативных Geologica (wght 700, SHRP 100) и Onest (400, 600) с кириллицей и казахскими
буквами, лежат в assets/fonts/pdf/ вместе с OFL; скрипт сборки и хэши — в репозитории. QR —
вектор из матрицы qrcode, ведёт на /{locale}/cert/{number}. Флаг CERT_PDF; вне демо нужен
https-адрес NEXT_PUBLIC_SITE_URL (D-025), без него маршрут отвечает 503. Флаг выключен —
печать браузером, как раньше.
Почему. Печать браузером зависит от настроек человека: поля, колонтитулы, масштаб. react-pdf
не задаёт оси вариативного шрифта и не подставляет запасной шрифт по unicode-range, поэтому
нужен один статический файл на начертание.
Отвергли. Headless Chromium на сервере — сотни МБ, не помещается в serverless-демо. Хранить
PDF в БД или на диске — копия ПДн и инвалидация при смене названия курса. Шрифты fontsource
или Google CDN — срезы с SHRP=0, разбиение по подмножествам, внешний запрос во время работы.

## D-035 · 2026-10-19 · Юридические документы в репозитории, согласие хранит хэш текста
Статус: принято оркестратором; тексты готовит и утверждает юрист ЦРП, число галочек на покупке — за владельцем
Решение. Оферта, политика обработки ПДн, согласие на обработку ПДн и условия возврата —
markdown-файлы content/legal/<doc>/<версия>.<ru|kz>.md. Реестр версий с SHA-256 —
src/lib/legal/registry.ts, тест сверяет хэши. Строка consents хранит вид, версию, язык,
контекст (регистрация или заказ) и text_sha256. Копия принятого текста — в legal_texts
(адресация по хэшу, только вставка). Форма отправляет токен показанных версий; если редакция
сменилась, согласие отмечается заново. Число галочек на покупке — предложено, ждёт
владельца: две (оферта с условиями возврата и согласие на ПДн) или одна. Флаг LEGAL; вне
демо он действует, только если у всех четырёх документов есть утверждённые ru- и kz-тексты
(D-025). Пока документов нет, согласия пишутся как раньше
(версия 2026-10-19, без хэша). Тексты документов — контент, а не строки интерфейса, поэтому
они не в messages/*.json.
Почему. Нужно доказать, с каким именно текстом согласился человек, а не только номер
версии. Тексты меняются редко и через ревью, редактор в админке не окупается. Копия в БД
переживёт перенос репозитория и попадает в бэкапы.
Отвергли. Тексты в БД с редактором — больше кода и атак, правки без ревью. Тексты в
messages/*.json — длинный документ в JSON не проверить. Только строка версии без хэша —
правка файла без новой версии останется незамеченной.

## D-034 · 2026-10-19 · Файлы: локальное хранилище в РК, выдача только через маршрут с проверкой доступа
Статус: принято оркестратором; владелец может отменить; лимиты, квоты, форматы и антивирус — за владельцем
Решение.
- Байты файлов — на сервере ЦРП в каталоге STORAGE_DIR (вне public/ и вне каталога
  приложения), метаданные — в таблице files. Абстракция src/lib/storage; S3-совместимое
  хранилище в РК подключается конфигом после решения ЦРП.
- Загрузка — route handler POST /api/uploads с потоковой записью и лимитом размера; лимит
  тела server actions остаётся 1 МБ. Загружает только admin.
- Тип файла определяется по сигнатуре: PNG, JPEG, WebP, PDF, DOCX, XLSX без макросов. SVG,
  HTML, архивы, старые DOC и XLS не принимаются. Из изображений удаляются EXIF и XMP.
- Выдача — только GET /api/files/[id] с проверкой доступа на каждый запрос. Документы —
  attachment, у всех ответов nosniff и CSP sandbox. Нет доступа — 404, гостю — вход.
- Ссылки уроков на файлы — таблица lesson_files, пересобирается при сохранении урока.
  Слушатель получает только файлы опубликованного урока, к которому у него есть доступ.
  Неиспользуемые файлы старше 24 часов удаляются подметанием.
- В демо файлы лежат во временном каталоге экземпляра; на Vercel и Netlify лимит 4 МБ.
Почему. D-009: платный контент и возможные ПДн остаются на сервере в РК. Доступ проверяется
на каждый запрос, как для уроков (BUILD §4). Server action буферизует тело до проверки прав.
Отвергли. Server action для загрузки. Файлы в public/ или статикой nginx — платный материал
доступен по ссылке, каталог релиза пересоздаётся при каждой выкладке (D-027). bytea в Postgres — раздувает БД и бэкапы.
Доступ «файл → курс» без учёта ссылок урока — открывает черновики и удалённые материалы.

## D-033 · 2026-10-19 · Напоминания о сроках: скрипт по крону, одно письмо на срок
Статус: принято оркестратором; частоту сводки руководителю решает владелец
Решение. scripts/send-reminders.ts запускается кроном сервера ежечасно с 09:00 до 19:00 по
Астане. Он ставит в очередь письма «скоро срок» (за 0–3 дня) и «срок прошёл» (не позже 30 дней
после срока) сотрудникам с назначениями, а также недельную сводку менеджерам организации.
Письмо «назначен курс» ставится в транзакции назначения. От дублей защищает
mail_outbox.dedupe_key UNIQUE: ключ включает зачисление и срок, а для сводки — организацию,
менеджера и неделю. Данные — из отчёта руководителя (buildTeamReport). HTTP-маршрута и
CRON_SECRET нет. В демо вместо крона — кнопка «Сформировать напоминания» в админке. Флаг REMINDERS.
Почему. Скрипт ходит в БД сам, наружу ничего не открыто. Уникальный ключ защищает от дублей
при параллельных запусках. Отчёт руководителя уже даёт статусы и изоляцию организаций.
Отвергли. HTTP-маршрут с секретом для крона — лишняя открытая точка и секрет в
crontab. Отдельная таблица отправленных напоминаний — дублирует очередь писем.

## D-032 · 2026-10-19 · Покупка гостем = регистрация и подтверждение email (уточняет D-020, #25)
Статус: принято оркестратором; владелец может отменить; обязательность подтверждения для заказа — вопрос владельцу
Решение. Аккаунтов без пароля и заказов без аккаунта не создаём. Гость регистрируется сам
(пароль задаёт при регистрации), получает письмо подтверждения и после подтверждения
оформляет заказ на свой аккаунт из сессии (D-020). Предложено, ждёт владельца: при активном
EMAIL_VERIFY createOrder отказывает (email_unverified), пока email аккаунта не подтверждён. Если кто-то заранее
зарегистрировал чужой email, владелец почты возвращает аккаунт через сброс пароля: пароль
заменяется, сессии захватчика закрываются, email подтверждается. Ссылки установки пароля
(D-020) нет.
Почему. Инвариант D-020 сохраняется: заказ принадлежит владельцу сессии, по email ничего не
ищется. Захват чужого email не даёт оформить заказ.
Отвергли. Заказ без аккаунта (user_id NULL до подтверждения) — ломает правило «NULL = аккаунт
удалён» и позволяет оплатить непривязанный заказ. Регистрация «сначала email, пароль по
ссылке» убрала бы перечисление через «аккаунт уже есть», но добавляет шаг для бесплатных
курсов. Вернёмся к ней, если перечисление станет проблемой.

## D-031 · 2026-10-19 · Одноразовые ссылки: в БД только хэш, токен — во фрагменте URL
Статус: принято оркестратором
Решение. Токены сброса пароля (1 час) и подтверждения email (3 дня) — 32 случайных байта, в
auth_tokens хранится только SHA-256. Токен одноразовый (атомарный UPDATE … WHERE used_at IS
NULL). Новый запрос гасит прежние токены и снимает с отправки их письма. Снимок email сверяется
при использовании. В ссылке токен стоит после «#», страница отправляет его POST-запросом.
Сброс пароля закрывает все сессии аккаунта и подтверждает email. Подтверждение email не
выполняет вход. Сырой токен лежит в очереди писем, пока письмо не ушло или ссылка не истекла.
Почему. Фрагмент не попадает в журналы сервера и Referer, а GET не тратит токен (сканеры
ссылок в почте). Ссылка сброса доказывает владение ящиком.
Отвергли. ?token= в query — остаётся в журналах прокси. bcrypt для токенов — лишняя нагрузка
на CPU при 256 битах случайности.

## D-030 · 2026-10-19 · Почта: очередь в БД, по умолчанию письма наружу не уходят
Статус: принято оркестратором; почтового провайдера выбирает владелец (D-009)
Решение. Письма ставятся в таблицу mail_outbox в транзакции действия и отправляются скриптом
scripts/mail-worker.ts по крону раз в минуту, с повторами (до 5 попыток). По умолчанию
транспорт outbox: письмо только сохраняется, админ видит его на странице «Письма». В демо
транспорт всегда outbox, ссылку из письма видно только там. Внешний транспорт подключается
конфигом после решения владельца; зависимость (nodemailer или клиент HTTP API провайдера)
добавляется вместе с адаптером, не раньше. Пока транспорт outbox, сброс пароля, подтверждение
email и напоминания в production не активны (D-025). Письма хранятся 90 дней.
Почему. ПДн не уходят за рубеж без решения ЦРП. Провайдер не выбран, а адаптер без настоящего
сервера не проверить. Очередь в БД переживает перезапуски и даёт повторы.
Отвергли. Resend по умолчанию — зарубежный сервис, нужно решение ЦРП (D-009). Письма «в консоль» — токены в
журналах. Отправка прямо из запроса — нет повторов, ответ ждёт почтовый сервер.

## D-029 · 2026-10-19 · Бэкапы: ежедневный pg_dump, шифрование на открытые ключи, копия только в РК
Статус: предложено (ждёт владельца: где вторая копия в РК, кто хранит ключи, приемлем ли RPO 24 ч)
Решение. Каждую ночь pg_dump в формате custom с проверкой, что архив читается; по
воскресеньям — полное восстановление в проверочную БД со сверкой таблиц и миграций. Архив
шифруется age на открытые ключи двух хранителей, приватного ключа на сервере нет. Хранение:
14 ежедневных, 8 недельных, 6 месячных копий. Каталог загруженных файлов — отдельный
зашифрованный архив каждую ночь. Вторая копия — только у другого провайдера в РК. Учебное
восстановление с настоящим ключом — раз в месяц по docs/ops/RUNBOOK.md. RPO — 24 часа.
Почему. Украденная копия без ключа бесполезна. Бэкап без проверки восстановления — не бэкап.
Копия за рубежом — трансграничная передача (D-009).
Отвергли. gpg с паролем на сервере — пароль лежит рядом с копией. WAL-архив и
восстановление на момент времени в MVP — сложнее в работе и восстановлении; вернёмся после
подключения эквайринга (D-007).

## D-028 · 2026-10-19 · /api/health публичный и без деталей, журналы nginx без query string
Статус: принято оркестратором
Решение. GET /api/health отдаёт статус БД и миграций, id релиза и время: 200 или 503,
Cache-Control: no-store, без текстов ошибок, хостов, имён таблиц и ПДн. Частоту ограничивает
nginx. Журнал nginx пишет путь без query string и без Referer. Route handlers разрешены для

Почему. Health нужен выкладке, откату и монитору без входа. В query бывают ключи заказов.
Отвергли. Health за авторизацией — секрет у монитора и в скриптах. Подробный health с
текстами ошибок — раскрывает внутреннее устройство.

## D-027 · 2026-10-19 · Выкладка на сервер ЦРП: каталог на релиз, симлинк, PM2 cluster с одним процессом
Статус: принято оркестратором; владелец может отменить (отступление от #24: сборка на сервере из тега, а не в CI)
Решение. Оператор запускает на сервере deploy.sh <тег>. Тег — потомок main с зелёным CI.
Релиз собирается из git-тега в отдельном каталоге releases/<id> с NEXT_DEPLOYMENT_ID. Порядок:
проверка окружения (ops-preflight), бэкап при новых миграциях (как именно — D-029,
предложено), миграции от владельца схемы,
права, проверка нового релиза на отдельном порту, атомарная замена симлинка current,
pm2 startOrReload (cluster, один процесс), проверка /api/health. При сбое после переключения —
автоматический откат. Статику всех живых релизов nginx отдаёт из общего каталога. Откат —
rollback.sh, БД не откатывается: миграции только добавляют. Крон — в UTC, скрипты
запускаются через run-script.sh с flock и timeout. В репозитории — шаблоны без секретов и IP и
docs/ops/RUNBOOK.md.
Почему. Подмена .next на месте оставляет окно без сборки: процесс падает при рестарте, а у
открытых страниц ломаются server actions старой сборки.
Лимиты частоты живут в памяти одного процесса (D-018, D-022). На проде ровно тот код, что в теге.
Отвергли. fork и pm2 restart — 502 при каждой выкладке. Cluster из 2+ процессов — лимиты
слабеют в N раз. Blue/green на двух портах — запасной вариант, больше движущихся частей.
Сборка в CI и доставка артефакта — SSH-ключ к серверу в секретах CI, адрес сайта вшивается
при сборке. Docker — лишний слой для одного процесса (D-004).

## D-026 · 2026-10-19 · Роли БД; в production миграции применяет только выкладка
Статус: принято оркестратором; владелец может отменить
Решение. В production две роли Postgres. crp_owner владеет схемой и выполняет DDL; им
пользуются только db-migrate и db-grants во время выкладки. crp_app — приложение, крон и
CLI: SELECT, INSERT, UPDATE, DELETE; audit_log — только SELECT и INSERT; schema_migrations —
только SELECT. Права выдаёт идемпотентный deploy/postgres/grants.sql после каждого прогона
миграций. В production с DATABASE_URL приложение миграции не накатывает: getDb() проверяет
их (assertMigrated) и не стартует, если есть ненакатанные. Явное исключение —
DB_MIGRATE_ON_START=1. Демо, разработка и тесты накатывают миграции сами. Скрипты открывают
БД через prepareDb(), а не migrate(). Журнал действий пишет одна функция writeAudit
(src/lib/audit.ts); actor_id NULL — система, крон, CLI.
Почему. Инъекция или RCE в приложении не получает DDL и не может править журнал. Прод не
работает на схеме старее кода. Страницы и скрипты входят в БД одинаково.
Отвергли. Одна роль-владелец — вся база доступна приложению. Миграции при
старте в production — DDL от рантайма и гонки нескольких процессов.

## D-025 · 2026-10-19 · Флаги функций: один модуль; в демо включены, в production — выключатель и готовность
Статус: принято оркестратором; владелец может отменить
Решение. Новые функции PASSWORD_RESET, EMAIL_VERIFY, REMINDERS, UPLOADS, LEGAL, CERT_PDF
включаются переменными FEATURE_<ИМЯ>=1 или 0. Если переменная не задана, функция включена в
демо и выключена в остальных случаях; другое значение — выключено. Код проверяет только
isFeatureActive(name) из src/lib/features.ts: выключатель и условия готовности. Вне демо
почтовым функциям нужны подключённая почта (MAIL_TRANSPORT не outbox) и https-адрес
NEXT_PUBLIC_SITE_URL, PDF сертификата — адрес, юридическим документам — утверждённые ru- и
kz-тексты всех четырёх документов. Значение считает сервер, клиент получает его пропсом.
E2E идут на демо, где все флаги включены; поведение при выключенном флаге проверяют
интеграционные тесты.
Почему. AGENTS.md: новые функции выходят выключенными до приёмки, а владелец принимает их
на демо по ссылке. Проверка готовности не даёт включить функцию, которая сломает поток в
проде: без почты EMAIL_VERIFY заблокировал бы все заказы, без адреса QR вёл бы на localhost.
Отвергли. Своя проверка в каждом модуле — условия расходятся. Флаги в БД с переключателем в
админке — включение без выкладки и ревью. Выключено по умолчанию и в демо — владелец не
увидит функцию, пока кто-то не поправит переменные площадки.

## D-024 · 2026-10-19 · Демо-превью также на Netlify
Статус: принято (запрос владельца: «сам закинь» — выложить демо самому)
Решение. Демо выкладываем на Netlify (сайт `crp-academy-demo`) только с явной
переменной сайта `DEMO_MODE=1`. Данные — сид в памяти, при перезапуске

## D-022 · 2026-10-19 · Лимиты без общего ведра; покупатель отменяет свой заказ; гонки — на Postgres
Статус: принято оркестратором; владелец может отменить
Решение.
- Лимит заказов: сначала на аккаунт, потом на известный IP. При неизвестном
  IP общего ведра нет: покупатель всегда вошёл (D-020), лимита на аккаунт
  хватает.
- Проверка сертификата при неизвестном IP — лимит на номер сертификата вместо
  общего ведра. Остаточный риск перебора номеров описан в BUILD.md §5.
- Владелец отменяет свой неоплаченный заказ сам (только по сессии, не по ключу
  из ссылки), журнал `order.cancel_by_owner`. Если открытый заказ оформлен
  иначе, чем новая форма, страница заказа об этом говорит.
- При возврате кандидаты на перенос доступа блокируются `SELECT … FOR UPDATE`.
  Интеграционные тесты в CI идут ещё и на Postgres 16; тесты гонок — только там.
Почему. Общее ведро для неизвестного IP — это блокировка всех покупок или
проверок одним скриптом. Без отмены своего заказа нельзя сменить способ
оплаты: второй открытый заказ не создаётся (D-020). PGlite — одно соединение,
гонки на нём не воспроизводятся. Тест одновременных возвратов без блокировки
падает на Postgres.
Отвергли. Общее ведро «до» лимита на номер — скрипт с разными номерами всё
равно блокирует всех. Обновлять открытый заказ данными новой формы — меняется
счёт, который мог уже уйти в бухгалтерию. Уровень изоляции SERIALIZABLE для
возврата — нужны повторы транзакций по всему коду.

## D-021 · 2026-10-19 · Детали D-020: срок при переходе доступа, старые заказы, перевод урока
Статус: принято оркестратором; владелец может отменить
Решение.
- При возврате доступ переходит на другой оплаченный заказ, только если срок
  того заказа ещё идёт (`paid_at + access_days`). Конец срока — этот же, не
  от «сейчас»: `enroll` получает явный `expiresAt`.
- Миграция `orders.access_days` один раз заполняет старые заказы сроком
  текущего предложения: колонка и заполнение — в одном DO-блоке.
- Казахская версия урока показывается, только если в ней есть все тесты
  русской (по id блока). Иначе слушатель видит русскую. Админка не сохраняет
  непустую казахскую версию с другим набором тестов.
- `markPaid` отказывает (`no_user`), если у заказа нет аккаунта. У ожидающих
  заказов сида есть аккаунты покупателей.
Почему. `accessDays` от «сейчас» дарил бы год: возврат продления оживил бы
давно истёкший заказ. NULL в старых заказах значил бы «бессрочно» для курса
на 365 дней. Перевод без теста позволял пройти урок, сменив язык.
Отвергли. Заполнять `access_days` при каждом прогоне миграции — перезапишет
снимок «бессрочно». Требовать в любой локали сумму тестов ru и kz — слушатель
должен был бы сдать тест, которого не видит.

## D-020 · 2026-10-19 · Покупка — только после входа; тест без подсказок при провале
Статус: принято (до задачи #25)
Решение.
- Оформить заказ можно только вошедшему пользователю. Заказ привязывается к
  аккаунту из сессии и никогда не ищется по email.
- Гостевая покупка — после подтверждения email и ссылки установки пароля (#25).
- Срок доступа фиксируется в заказе при оформлении.
- При возврате снимается только доступ по этому заказу. Если у человека есть
  другой оплаченный заказ на курс, доступ переходит на него.
- Повторный заказ на тот же курс, пока есть неоплаченный, не создаётся:
  возвращается открытый.
- Результат теста при провале — только «не сдан», без счёта (уточнено
  2026-10-19 после проверки: изначально оставляли счёт). Счёт, разбор по
  вопросам и пояснения — после сдачи.
Почему. Ревью нашло захват покупки через заранее зарегистрированный чужой email
и оплаченный аккаунт без пароля. Ещё один риск — подбор ответов по разбору
каждой попытки. По одному счёту ответы тоже подбираются: меняешь ответ на один
вопрос и смотришь, вырос ли счёт.

## D-018 · 2026-10-19 · Лимиты входа: доверенный IP и лимит на аккаунт
Статус: принято
Решение. IP клиента берётся только по доверенной схеме: `TRUSTED_PROXY_HOPS=N` —
N-е значение X-Forwarded-For справа; при 0 (по умолчанию) X-Forwarded-For не
читается, X-Real-IP — только при `TRUST_X_REAL_IP=1` (Vercel). Неизвестный IP —
общее щедрое ведро. Независимо от IP действует лимит на email (вход — 20 за
15 минут). Хранилище лимитов ограничено; при переполнении первыми вытесняются
ключи с малым числом попыток, а не «давно созданные».
Почему. Первое значение X-Forwarded-For присылает клиент — по нему лимит
обходится сменой заголовка. Лимит на аккаунт защищает от перебора с множества IP.
Отвергли. Доверять X-Forwarded-For целиком — подделка IP. Лимиты в Postgres/Redis —
лишняя запись на каждый вход и внешний сервис; для MVP хватает памяти процесса.
Цена: злоумышленник может временно заблокировать вход в чужой аккаунт (20 попыток).

## D-017 · 2026-10-19 · Зачисление: повтор заказа — no-op, новая выдача заменяет источник
Статус: принято
Решение. `enroll` с тем же `orderId`, что в строке, ничего не меняет ни в каком
состоянии (после возврата повтор «оплачено» доступ не возвращает). Любая другая

даёт `self`, даже если offer неактивен.
Почему. Ревью нашло: повтор заказа снимал отзыв после возврата; «хвосты» прежнего
источника приводили к отзыву чужого доступа; пауза продаж открывала платный курс.

## D-005 · 2026-10-19 · Ядро курсов берём из «Академии» SalemAI копированием
Статус: принято
Решение. Модель «сайт → дерево (курс / модуль / урок) → блоки», квизы с
серверным подсчётом, прогресс и сертификаты с публичной проверкой копируем из
ветки `feat/academy` репозитория SalemAI в этот репозиторий и доводим. Ветку в
SalemAI не трогаем.
Почему. Ядро сделано чисто, изолировано и покрыто тестами, это экономит недели.
Отвергли. Форк всего монолита SalemAI: тянет большой объём чужих доменов и таблиц.
Растить LMS внутри SalemAI: привязывает ЦРП к деплою, флагам и бренду SalemAI.

## D-004 · 2026-10-19 · Стек как в SalemAI
Статус: принято
Решение. Next.js 16 + React 19 + TS strict + Tailwind 4 + PostgreSQL (postgres.js
без ORM) + session-auth (cookie + bcrypt) + next-intl (ru и казахский: `/kz` в URL,
`kk` для `Intl`, см. D-002) + node:test и Playwright.
Конвенции БД: TEXT id, BIGINT epoch-мс, деньги в BIGINT тенге, идемпотентные
миграции.
Почему. Один разработчик и общие агенты работают в обоих репозиториях. Код,
паттерны и люди взаимозаменяемы.
Отвергли. Готовые LMS (GetCourse, iSpring, Moodle): нет контроля над доступами,
брендом и интеграцией с CRM ЦРП, ежемесячная оплата за пользователя.

## D-003 · 2026-10-19 · Отдельный репозиторий `crp-kz` для LMS
Статус: принято
Решение. Платформа обучения ЦРП живёт в отдельном репозитории `salemaikz/crp-kz`.
Другие системы SalemAI для ЦРП остаются в своих репозиториях.
Почему. Работы по ЦРП идут параллельно в разных сессиях, раздельные
репозитории исключают конфликты. У LMS свой бренд (ЦРП), свой цикл релизов и
своя аудитория (клиенты ЦРП).
Отвергли. Модуль внутри SalemAI — см. D-005.

## D-002 · 2026-10-19 · Языки: русский и казахский
Статус: принято
Решение. Локали `ru` (по умолчанию) и казахский. В URL и именах файлов
казахский обозначается `kz`, как в SalemAI. Для `Intl` (даты, числа,
плюрализация), `<html lang>` и `hreflang` используется ISO-код `kk`: `kz` — это
код страны. Контент курса хранится по локалям. Если перевода нет,
показывается русская версия с пометкой. Английский — по запросу ЦРП.
Почему. Клиенты ЦРП — предприниматели Казахстана.

## D-001 · 2026-10-19 · Работа ведётся через GitHub
Статус: принято
Решение. Задачи — issues, работа — ветки и PR, решения — этот файл, передача
между сессиями — `docs/handoffs/`. Договорённости из чатов и артефактов, не
перенесённые сюда, считаются несуществующими.
Почему. Несколько параллельных сессий по ЦРП; без общего источника истины они
пересекаются.
