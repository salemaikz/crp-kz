# Журнал решений

Нетривиальные решения по проекту: что решили, почему, что отвергли. Новые записи —
**сверху**. Формат записи:

```
## D-NNN · YYYY-MM-DD · Заголовок
Статус: принято | предложено (ждёт владельца) | отменено (см. D-MMM)
Решение. Одно-два предложения.
Почему. Ключевые причины.
Отвергли. Варианты и почему нет.
```

`предложено` — значит решает владелец; агенты не считают это принятым.

## D-021 · 2026-10-19 · Детали D-020: срок при переходе доступа, старые заказы, перевод урока
Статус: принято оркестратором; владелец может отменить
Решение.
- При возврате доступ переходит на другой оплаченный заказ, только если срок
  того заказа ещё идёт (`paid_at + access_days`). Конец срока — этот же, не
  от «сейчас»: `enroll` получает явный `expiresAt`.
- Миграция `orders.access_days` один раз заполняет старые заказы сроком
  текущего предложения: колонка и заполнение — в одном DO-блоке.
- Казахская версия урока показывается, только если в ней есть все тесты
  русской (по id блока). Иначе слушатель видит русскую. Админка не сохраняет
  непустую казахскую версию с другим набором тестов.
- `markPaid` отказывает (`no_user`), если у заказа нет аккаунта. У ожидающих
  заказов сида есть аккаунты покупателей.
Почему. `accessDays` от «сейчас» дарил бы год: возврат продления оживил бы
давно истёкший заказ. NULL в старых заказах значил бы «бессрочно» для курса
на 365 дней. Перевод без теста позволял пройти урок, сменив язык.
Отвергли. Заполнять `access_days` при каждом прогоне миграции — перезапишет
снимок «бессрочно». Требовать в любой локали сумму тестов ru и kz — слушатель
должен был бы сдать тест, которого не видит.

## D-020 · 2026-10-19 · Покупка — только после входа; тест без подсказок при провале
Статус: принято (до задачи #25)
Решение.
- Оформить заказ можно только вошедшему пользователю. Заказ привязывается к
  аккаунту из сессии и никогда не ищется по email.
- Гостевая покупка — после подтверждения email и ссылки установки пароля (#25).
- Срок доступа фиксируется в заказе при оформлении.
- При возврате снимается только доступ по этому заказу. Если у человека есть
  другой оплаченный заказ на курс, доступ переходит на него.
- Повторный заказ на тот же курс, пока есть неоплаченный, не создаётся:
  возвращается открытый.
- Результат теста при провале — только счёт. Разбор по вопросам и пояснения —
  после сдачи.
Почему. Ревью нашло захват покупки через заранее зарегистрированный чужой email
и оплаченный аккаунт без пароля. Ещё один риск — подбор ответов по разбору
каждой попытки.

## D-019 · 2026-10-19 · Исключение: превью на Vercel включает демо само
Статус: принято оркестратором; владелец может отменить
Решение. На Vercel (`VERCEL=1`) без `DATABASE_URL` демо-режим включается без
`DEMO_MODE=1`. Импорт репозитория в Vercel тогда работает без настройки
переменных.
Почему. Vercel по D-009 и D-015 — только площадка демо без реальных ПДн. Прод —
сервер ЦРП в РК с `DATABASE_URL`. Если прод когда-нибудь окажется на Vercel,
решение нужно отменить и вернуть явный флаг.
Отвергли. Обязательный `DEMO_MODE=1` на Vercel — лишний шаг при импорте, при
этом защиты не добавляет: реальных данных на Vercel быть не должно.

## D-018 · 2026-10-19 · Лимиты входа: доверенный IP и лимит на аккаунт
Статус: принято
Решение. IP клиента берётся только по доверенной схеме: `TRUSTED_PROXY_HOPS=N` —
N-е значение X-Forwarded-For справа; при 0 (по умолчанию) X-Forwarded-For не
читается, X-Real-IP — только при `TRUST_X_REAL_IP=1` (Vercel). Неизвестный IP —
общее щедрое ведро. Независимо от IP действует лимит на email (вход — 20 за
15 минут). Хранилище лимитов ограничено; при переполнении первыми вытесняются
ключи с малым числом попыток, а не «давно созданные».
Почему. Первое значение X-Forwarded-For присылает клиент — по нему лимит
обходится сменой заголовка. Лимит на аккаунт защищает от перебора с множества IP.
Отвергли. Доверять X-Forwarded-For целиком — подделка IP. Лимиты в Postgres/Redis —
лишняя запись на каждый вход и внешний сервис; для MVP хватает памяти процесса.
Цена: злоумышленник может временно заблокировать вход в чужой аккаунт (20 попыток).

## D-017 · 2026-10-19 · Зачисление: повтор заказа — no-op, новая выдача заменяет источник
Статус: принято
Решение. `enroll` с тем же `orderId`, что в строке, ничего не меняет ни в каком
состоянии (после возврата повтор «оплачено» доступ не возвращает). Любая другая
выдача заменяет источник целиком (`org_id`, `order_id`, `granted_by`, `due_at` —
из input или NULL); срок действующего доступа не сокращается. `revokeEnrollment`
принимает фильтр `{ orderId?, orgId? }`: возврат заказа A не отзывает доступ,
который уже держится на заказе B или назначении. Курс с offer цены > 0 никогда не
даёт `self`, даже если offer неактивен.
Почему. Ревью нашло: повтор заказа снимал отзыв после возврата; «хвосты» прежнего
источника приводили к отзыву чужого доступа; пауза продаж открывала платный курс.
Отвергли. Отдельная таблица грантов на каждый источник (несколько строк на пару
user/course) — точнее, но меняет контракт §4 и модели всех фич; вернёмся при B2B-местах.

## D-016 · 2026-10-19 · Демо-режим только по явному флагу
Статус: принято
Решение. `isDemo()` = `DEMO_MODE=1` или локальная разработка без `DATABASE_URL`
(`NODE_ENV` не production). В production без `DATABASE_URL` и без `DEMO_MODE=1`
инициализация БД падает (fail closed). Исключение для Vercel — D-019. Короткий `SESSION_SECRET` — ошибка и в
демо; демо-секрет подставляется только в демо на PGlite. На регистрации в демо —
предупреждение не вводить реальные ПДн.
Почему. Забытый `DATABASE_URL` в проде не должен тихо превращать сервер в демо с
публичным секретом сессии и кнопками входа под админом.
Отвергли. Демо по отсутствию `DATABASE_URL` (как было) — небезопасный дефолт.

## D-015 · 2026-10-19 · Демо-превью на Vercel со встроенной БД (PGlite)
Статус: принято
Решение. Чтобы владелец мог открыть платформу по ссылке до появления сервера ЦРП,
превью разворачивается на Vercel. Без `DATABASE_URL` приложение работает на
встроенном Postgres (PGlite) с демо-данными из сида; изменения живут до
перезапуска экземпляра. В демо нет реальных ПДн. Прод — сервер ЦРП в РК с
Postgres (D-009, issue #24). Слой БД один, драйверов два (`docs/lms/BUILD.md` §2).
Отвергли. Облачный Postgres для демо — лишний внешний сервис и ПДн за рубежом.

## D-009 · 2026-10-19 · Персональные данные — только в Казахстане
Статус: принято, юридическая проверка `[дозаполни: юрист ЦРП]`
Решение. БД платформы и файлы с ПДн хранятся на сервере в РК. Любой
зарубежный сервис — почта (например, Resend), видеохостинг, ИИ — это
трансграничная передача. Такие сервисы получают ПДн только в необходимом
минимуме, только после решения ЦРП и с согласием пользователя (галочка при
регистрации или покупке, версия текста хранится). Если для почты нет согласия
или оно не подходит, нужен сервис в РК. В ИИ-сессии разработки (Claude, Codex)
ПДн с прода не передаются вообще — только обезличенные данные.
Почему. Закон РК о персональных данных требует локализации баз с ПДн граждан
РК. По обзору, редакция с 25.08.2026 прямо относит к этому облака и
зарубежные ИИ. Текст закона не сверяли, поэтому нужна проверка юриста.

## D-007 · 2026-10-19 · Оплата: сначала вручную, потом эквайринг
Статус: предложено (ждёт владельца)
Решение. Фаза 0: заказ, затем счёт на юрлицо (PDF, по БИН) или Kaspi QR либо
перевод. Администратор отмечает «оплачено», и доступ выдаётся автоматически.
Фаза 1: интернет-эквайринг. Провайдера выбирает ЦРП, потому что договор
заключается с банком на ЦРП.

Кандидаты (обзор 19.10.2026, тарифы сверить при выборе):
- Kaspi Pay — удалённая оплата и QR. Для частных курсов около 0,95 %.
  Публичного API для сайта не нашли.
- TipTop Pay (бывший CloudPayments KZ) — от 2,5 %. Есть рекуррентные платежи и
  встроенная фискализация.
- Halyk ePay — 2,5–3 %.
- Freedom Pay — 3,5 %.
- ioka — индивидуально, есть решение для образования.

Слой провайдеров делаем по образцу абстракции `PaymentProvider` из SalemAI.
Интеграцию конкретного провайдера пишем и проверяем заново по его
документации и в тестовой среде. При оплате картой, через Kaspi или QR,
вероятно, нужен фискальный чек — через провайдера или онлайн-кассу
`[дозаполни: бухгалтер]`.

Почему.
- ЦРП и сейчас продаёт обучение по счёту.
- Клиенты консалтинга — во многом юрлица, им всё равно нужен счёт.
- Ручной путь запускается без договора с банком и не блокирует продажи.
Отвергли. Ждать эквайринг до первой продажи — долго и зависит от банка.
Задачи: #16 (Фаза 0), #18 (выбор провайдера), #19 (эквайринг).

## D-006 · 2026-10-19 · Оркестратор и уровни моделей
Статус: принято
Решение. Главная сессия Claude Code — оркестратор. Подзадачи раздаются
подагентам по уровням:
- T0 Haiku — поиск и механика;
- T1 Sonnet — реализация по ТЗ и тесты;
- T2→T1 — дизайн и ревью на Opus, реализация на Sonnet;
- T2 Opus — архитектура, деньги, доступы, ревью.

Модели зашиты во frontmatter `.claude/agents/*.md`. Подагенты без явной модели
идут на Sonnet (`CLAUDE_CODE_SUBAGENT_MODEL`). Frontmatter важнее этой
переменной начиная с Claude Code v2.1.251. Ревью перед пушем всегда на Opus.
Подробности — `docs/agents/ROUTING.md`.
Почему. Основной расход лимитов — чтение кода и рутина. Их выполняют младшие
модели, а качество держат обязательное ревью на Opus и эскалация вверх при неудаче.
Отвергли. Всё на Opus — дорого. Всё на Sonnet без ревью Opus — риск в оплате и доступах.

## D-005 · 2026-10-19 · Ядро курсов берём из «Академии» SalemAI копированием

## D-004 · 2026-10-19 · Стек как в SalemAI
Статус: принято
Решение. Next.js 16 + React 19 + TS strict + Tailwind 4 + PostgreSQL (postgres.js
без ORM) + session-auth (cookie + bcrypt) + next-intl (ru и казахский: `/kz` в URL,
`kk` для `Intl`, см. D-002) + node:test и Playwright.
Конвенции БД: TEXT id, BIGINT epoch-мс, деньги в BIGINT тенге, идемпотентные
миграции.
Почему. Один разработчик и общие агенты работают в обоих репозиториях. Код,
паттерны и люди взаимозаменяемы.
Отвергли. Готовые LMS (GetCourse, iSpring, Moodle): нет контроля над доступами,
брендом и интеграцией с CRM ЦРП, ежемесячная оплата за пользователя.

## D-002 · 2026-10-19 · Языки: русский и казахский
Статус: принято
Решение. Локали `ru` (по умолчанию) и казахский. В URL и именах файлов
казахский обозначается `kz`, как в SalemAI. Для `Intl` (даты, числа,
плюрализация), `<html lang>` и `hreflang` используется ISO-код `kk`: `kz` — это
код страны. Контент курса хранится по локалям. Если перевода нет,
показывается русская версия с пометкой. Английский — по запросу ЦРП.
Почему. Клиенты ЦРП — предприниматели Казахстана.

## D-001 · 2026-10-19 · Работа ведётся через GitHub
Статус: принято
Решение. Задачи — issues, работа — ветки и PR, решения — этот файл, передача
между сессиями — `docs/handoffs/`. Договорённости из чатов и артефактов, не
перенесённые сюда, считаются несуществующими.
Почему. Несколько параллельных сессий по ЦРП; без общего источника истины они
пересекаются.
