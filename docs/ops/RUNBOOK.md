# RUNBOOK: платформа обучения ЦРП на сервере в Казахстане

Как поставить, выложить, откатить, восстановить и разобрать сбой. Решения: D-026 (роли БД),
D-027 (выкладка), D-028 (health и журналы), D-029 (бэкапы, **предложено, ждёт владельца**).
Статусы решений ведёт только `DECISIONS.md`. Проект комплекта: `docs/lms/design/ops.md`.
Файлы комплекта лежат в `deploy/`, обзор — `deploy/README.md`.

В репозитории нет и не должно быть IP, паролей и ключей. Везде ниже `<значение>` означает
«вносит оператор на сервере». Секреты живут в `/etc/crp` и в менеджере паролей владельца.

## Ждёт решения владельца

Пока решения нет, комплект работает с безопасными значениями по умолчанию. Это не готовая
эксплуатация, а рабочая заготовка.

| Вопрос | Где в комплекте | Что происходит до решения |
|---|---|---|
| Где вторая копия бэкапов в РК | `BACKUP_REMOTE`, `BACKUP_REMOTE_SSH_KEY`, `BACKUP_FILES_REMOTE`, `BACKUP_FILES_REMOTE_SSH_KEY` в `backup.env` | Копия только на этом сервере, `offsite=false` в статусе. Потеря сервера означает потерю данных вместе с бэкапом. Если задан `BACKUP_REMOTE` или `BACKUP_FILES_REMOTE`, а отправка не прошла (в том числе для файлов не задан свой ключ, D-041), `healthcheck.sh` показывает предупреждение `backup_offsite`, а через 48 часов подряд шлёт алерт |
| Кто хранит приватные ключи age | `BACKUP_AGE_RECIPIENTS_FILE` (только открытые ключи) | `backup.sh` не запускается: в файле заглушки `age1<...>`. Из-за этого любая выкладка с ненакатанными миграциями, в том числе первая на пустую БД, останавливается с кодом 2 на шаге бэкапа, пока нет настоящих открытых ключей (D-029 предложено). Обходного пути без бэкапа нет; если владелец разрешит иной порядок для первой выкладки на пустую БД, это записывается в `DECISIONS.md`, а не делается молча |
| Приемлем ли RPO 24 часа | расписание в `deploy/cron/crp.cron` | Бэкап раз в сутки. Оплаты за последние сутки восстанавливаются по банковской выписке |
| Канал алертов, внешний монитор | `ALERT_TELEGRAM_*` в `monitor.env` | Алерты в journald и `/var/log/crp/healthcheck.log` |
| Хостер, домен, список людей с SSH | раздел 2 | Решает владелец |
| `includeSubDomains` для HSTS | `deploy/nginx/crp-security-headers.conf` | Не включён |

Копия бэкапа за пределами РК запрещена (D-009): трансграничная передача только по решению
ЦРП и юриста.

## 1. Схема

```
клиент -> nginx :443 -> 127.0.0.1:3000 (PM2 cluster, один процесс) -> Postgres 127.0.0.1:5432 (TLS)
```

Каталоги и владельцы:

```
/srv/crp/                      crpdeploy:crp 0751 (current меняет crpdeploy; группа crp без записи; o+x для nginx)
  repo.git/                    зеркало репозитория (crpdeploy)
  releases/<UTC>-<тег>/        crpdeploy:crp 2750 (setgid на releases: группа crp у новых релизов); .next/cache 2770
    RELEASE.json               {id, tag, sha, builtAt}
    .env.production            симлинк на /etc/crp/app.env
  current -> releases/<id>     атомарная замена симлинка
  shared/
    instance.json              {name, port, configDir, smokePort, deployBranch}
    static/_next/static/       статика всех живых релизов (читает nginx)
    maintenance/               страница обслуживания
    state/                     previous, deploy.log, deploy.lock, журналы сборки
/etc/crp/                      root:crp 0751 (x для всех: postgres читает backup.env)
  app.env          root:crp 0640        приложение и крон (роль crp_app)
  migrate.env      root:crpdeploy 0640  роль crp_owner, только выкладка
  backup.env       root:root 0644       настройки бэкапа, секретов нет
  monitor.env      root:crp 0640        домен и алерты
  backup-recipients.txt root 0644       открытые ключи age
/usr/local/lib/crp/            root 0755: копии скриптов (ставит install-ops.sh)
/var/lib/crp/files             crp 0700: STORAGE_DIR
/var/lib/crp-ops/              postgres:crp 1775 (sticky): статусы бэкапа и монитора; crp не удаляет файлы postgres
/var/log/crp/                  crp:adm 0750: журналы PM2 и крона приложения
/var/log/crp-backup/           postgres:adm 0750: журнал бэкапа БД (вне каталога crp, D-041)
/var/backups/crp/              root 0711: daily, weekly, monthly, manual (postgres 0700), files (crp 0700)
```

Владелец корня `/srv/crp` — `crpdeploy`: `deploy.sh` и `rollback.sh` создают в нём `current.tmp` и
переименовывают его в `current`. Для `crp` корень открыт только на чтение и проход (группа crp, r-x),
новых путей записи у приложения нет; подкаталоги `releases` (2750) и `shared` принадлежат `crpdeploy`.
Граница crpdeploy и root: `crpdeploy` может переименовать подкаталоги корня и подложить ссылку, а
`install-ops.sh` работает от root. Поэтому скрипт отказывает (код 2), если корень или его подкаталог
оказался ссылкой, и создаёт всё внутри корня от имени `crpdeploy`, без `chown` и `chmod` от root.
Нет права записи в корне означает код 2 и строку «нет права записи в <корень>» в `deploy.log`.

Пользователи ОС: `crp` запускает PM2 и крон приложения и только читает код; `crpdeploy`
собирает релизы и знает пароль владельца схемы. `sudoers` даёт `crpdeploy` ровно два права:
`pm2` от имени `crp` и `backup.sh --label pre-deploy-*` от имени `postgres`.

Роли БД: `crp_owner` (DDL, только выкладка), `crp_app` (приложение и крон; без DDL, `audit_log`
только дописывается), `postgres` (peer, только бэкап и разовые работы).

Один процесс в режиме cluster, а не несколько: лимиты частоты живут в памяти процесса
(D-018, D-022), при N воркерах они ослабли бы в N раз. `pm2 startOrReload` поднимает новый
воркер, ждёт готовности и только потом гасит старый.

## 2. Установка сервера с нуля

1. Ubuntu 24.04 LTS, `timedatectl set-timezone UTC`, `systemd-timesyncd`.
2. SSH только по ключам, `PermitRootLogin no`, `ufw allow 22,80,443`, `fail2ban` для sshd,
   `unattended-upgrades` (security), swap 2 ГБ.
3. Node 22 (NodeSource), `npm i -g pm2@<точная версия>`.
4. Пакеты: `apt install git nginx certbot python3-certbot-nginx age rsync jq acl` (`acl` нужен для
   удаления старых релизов, см. раздел 4).
5. Пользователи без пароля и без оболочки для входа:
   `useradd --create-home --shell /usr/sbin/nologin crp`, затем
   `useradd --create-home --shell /usr/sbin/nologin --groups crp crpdeploy` (crp для crpdeploy
   дополнительная группа). Группу новых релизов задаёт setgid на `releases` (его ставит
   `install-ops.sh`); `deploy.sh` останавливается с кодом 2, если группа релиза не `crp`.
   Корень и зеркало репозитория: `install -d -m 0751 -o crpdeploy -g crp /srv/crp`, затем
   `sudo -u crpdeploy git clone --mirror <адрес репозитория> /srv/crp/repo.git`. Зеркало принадлежит
   `crpdeploy` и нужно только для `deploy.sh`. Комплект для root (скрипты, sudoers, крон, nginx) из зеркала
   не берётся: скомпрометированный `crpdeploy` (например, через `postinstall` пакета при `npm ci`) мог бы
   переставить тег на свой коммит с `crpdeploy ALL=(ALL) NOPASSWD: ALL` в `deploy/sudoers/crpdeploy`,
   `visudo -c` такой файл пропустит, и он получил бы root (ops, риск 19). Поэтому комплект нужного тега
   root клонирует сам, от root, прямо из репозитория, в каталог root с правами 0755:
   `d=$(mktemp -d /tmp/crp-deploy.XXXXXX) && chmod 0755 "$d" && git clone --depth 1 --branch <тег> <адрес репозитория> "$d/crp"`
   (`<каталог выгрузки>` ниже, в шагах 6-8, — это `$d/crp`; `crpdeploy` и postgres должны его читать,
   `install-ops.sh` откажет с кодом 2, если выгрузка или её родители принадлежат не root либо доступны на запись другим; обход - только явный `--allow-foreign-owner`. Эта проверка не защищает от подмены тега в зеркале `repo.git`: защита - только клонирование от root мимо зеркала, не `git archive` из зеркала через tar). Сверьте, что
   `git -C "$d/crp" rev-parse HEAD` совпадает с sha выпущенного тега. Если адрес закрытый, ключи доступа
   у root вносит оператор вне репозитория, сюда они не пишутся.
6. `apt install postgresql-16`; положить `<каталог выгрузки>/deploy/postgres/postgresql.conf.d/crp.conf` в
   `conf.d`, строки из `deploy/postgres/pg_hba.snippet` в `pg_hba.conf`, перезапустить.
7. Роли и БД: `sudo -u postgres psql -v ON_ERROR_STOP=1 -v db=crp -v owner=crp_owner -v app=crp_app -f <каталог выгрузки>/deploy/postgres/roles.sql`,
   затем `\password crp_owner` и `\password crp_app`. Пароли сразу в менеджер паролей владельца.
8. Поставить комплект: `bash <каталог выгрузки>/deploy/bin/install-ops.sh --domain <домен>` (от root, из выгрузки
   шага 5). Обновление комплекта на новом теге: тот же `git clone --depth 1 --branch <новый тег>` в новый
   временный каталог от root и запуск `install-ops.sh` оттуда; зеркало `/srv/crp/repo.git` для этого
   не используется. Старые выгрузки удалите (`rm -r "$d"`). Без сертификата
   скрипт ставит только порт 80. Получить сертификат:
   `certbot certonly --webroot -w /var/www/certbot -d <домен>`, затем
   `install-ops.sh --domain <домен>` ещё раз (подключит TLS). Таймер `certbot.timer` с
   `--deploy-hook "systemctl reload nginx"`. Если `install-ops.sh` отвечает «символическая ссылка»,
   кто-то заменил подкаталог корня ссылкой (раздел 1, граница crpdeploy и root): выясните причину,
   удалите ссылку и запустите скрипт снова.
9. `shared/instance.json` создаётся install-ops.sh; для основной ветки, которой ещё нет в
   репозитории, задайте `deployBranch` от имени `crpdeploy`, а не от root (файл принадлежит `crpdeploy`,
   правка от root пошла бы по подложенной ссылке):
   `sudo -u crpdeploy sh -c 'jq ".deployBranch = \"<ветка>\"" /srv/crp/shared/instance.json > /srv/crp/shared/instance.json.new && install -T -m 0644 -g crp /srv/crp/shared/instance.json.new /srv/crp/shared/instance.json && rm -f /srv/crp/shared/instance.json.new'`
   (права 0644 и группа `crp`, как у install-ops.sh: `healthcheck.sh` работает от `crp` и читает этот файл).
10. Файлы `/etc/crp/*.env` по шаблонам `deploy/env/*.example`, права из раздела 1.
    `SESSION_SECRET` и ключ server actions создаются командой `openssl rand`, значения в
    репозиторий, чат и issue не попадают.
11. Открытые ключи age хранителей в `/etc/crp/backup-recipients.txt` (см. раздел 6).
12. Первая выкладка: `sudo -u crpdeploy /usr/local/lib/crp/deploy.sh vX.Y.Z`.
13. `sudo -u crp -H pm2 startup systemd -u crp --hp /home/crp`: pm2 выведет команду, её выполняет root. Затем `sudo -u crp -H pm2 save`.
14. Первый администратор (раздел 3), первый бэкап и учебное восстановление (раздел 6.2).

## 3. Первый администратор

```
sudo -u crp /usr/local/lib/crp/run-script.sh create-admin -- --email <почта> --name <имя> --owner-org-name "ЦРП" --owner-org-slug crp
```

Пароль вводится в приглашении дважды, в командной строке его нет. Демо-данных на проде нет:
preflight проверяет отсутствие пользователей `@crp.demo`.

### 3.1 Повышение существующего аккаунта (`--promote`)

Сотрудник уже зарегистрировался как слушатель: администратором его делают повышением, а не
повторным созданием (повтор даёт код 3, `exists`).

```
sudo -u crp /usr/local/lib/crp/run-script.sh create-admin -- --email <почта> --name <имя> --promote
```

- Пароль не спрашивается и не меняется. Все открытые сессии повышаемого закрываются (D-039):
  сессия, оставшаяся на общем компьютере или утёкшая раньше, не станет администраторской. Человек
  входит заново. Если он уже администратор, ничего не меняется.
- Адрес не подтверждён (письмом или иначе): команда останавливается с кодом 3, `unverified`,
  ничего не меняя. Регистрация открыта, и аккаунт на похожий адрес мог завести кто угодно.

### 3.2 Повышение с подтверждением личности (`--promote --identity-confirmed`, D-039)

Когда адрес не подтверждён, а письма (`EMAIL_VERIFY`, `PASSWORD_RESET`) ещё не включены, или
оператору нужна полная уверенность. Порядок:

1. Сотрудник находится рядом с оператором, у терминала оператора.
2. Оператор вводит команду с `--promote --identity-confirmed`. Сотрудник сам читает адрес в команде
   на экране и подтверждает, что это адрес его ящика. Оператор адрес не угадывает и не правит.
3. Скрипт спрашивает новый пароль дважды без эха: его вводит сам сотрудник, не оператор. Не короче
   12 символов.
4. В одной транзакции: роль `admin`, пароль заменён, адрес отмечен подтверждённым, все сессии
   закрыты, непогашенные ссылки на сброс пароля и подтверждение погашены. Сотрудник входит заново.

```
sudo -u crp /usr/local/lib/crp/run-script.sh create-admin -- --email <почта> --name <имя> --promote --identity-confirmed
```

`--identity-confirmed` без `--promote` отклоняется (код 2). Остаточный риск: опечатка в адресе. Если
оператор повысит аккаунт на похожий адрес, его владелец получит администратора через сброс пароля,
как только включат `PASSWORD_RESET`. Поэтому адрес сверяет сам сотрудник, а не оператор.

Коды выхода `create-admin`: 0 успех (создан, роль выдана или уже администратор); 2 неверные данные,
слабый пароль, неверный slug, ошибка в аргументах, демо без `--allow-demo`; 3 пользователь уже есть
(без `--promote`), не найден (с `--promote`) или адрес не подтверждён; 1 прочая ошибка.

В журнал аудита пишутся без почты и имени: `user.role_change` при повышении; при первом создании
ещё `user.create_admin`, `org.create` и `org.member_add`. В `meta` способ (`via: cli`), новая роль
(`to: admin`), число закрытых сессий (`sessionsRevoked`) и пометки `identity`,
`passwordReset`, `emailVerified`.

## 4. Выкладка

Тег ставится на основную ветку после зелёного CI. Затем на сервере:

```
sudo -u crpdeploy /usr/local/lib/crp/deploy.sh vX.Y.Z
```

Что делает скрипт (журнал: `/srv/crp/shared/state/deploy.log`):

1. Проверяет тег по шаблону `vX.Y.Z` и берёт блокировку: параллельная выкладка получает код 4.
2. `git fetch`; тег обязан входить в основную ветку, а CI для коммита быть зелёным
   (`--skip-ci-check` пропускает проверку и пишет предупреждение в журнал).
3. Выгружает тег в `releases/<id>` без `.git`, пишет `RELEASE.json`, подключает `.env.production`.
4. `npm ci --include=dev` строго по lock-файлу.
5. `ops-preflight --db`: любая ошибка останавливает выкладку, прод не тронут.
6. Собирает с `NEXT_DEPLOYMENT_ID=<id>`.
7. Добавляет статику релиза в общий каталог, ничего не удаляя.
8. Смотрит `db:status` и **разбирает код явно**: 0 означает «бэкап не нужен», 3 означает «есть
   ненакатанные миграции», тогда делается бэкап `pre-deploy-<id>`; любой другой код останавливает
   выкладку, прод не тронут. Скрипт не обрывается на коде 3 из-за `set -e`: код читается через
   `|| src=$?`.
9. Миграции от `crp_owner`: одна транзакция, блокировка, `lock_timeout`. Ошибка означает откат
   транзакции, прод работает на старом релизе.
10. `db-grants` выдаёт права приложения на новые объекты.
11. Запускает новый релиз на отдельном порту (`smokePort`) и ждёт `/api/health` с `status=ok` и
    `release=<id>`, затем `GET /ru` с кодом 200. Провал означает, что переключения нет.
12. Атомарно меняет `current`, прежний релиз записывает в `state/previous`.
13. `pm2 startOrReload` и `pm2 save`.
14. До 90 с ждёт `/api/health` с новым `release`. Не дождался: автоматический `rollback.sh`.
15. Оставляет 5 последних релизов, а также `current` и `previous`. Из общей статики удаляет только
    файлы, которых нет ни в одном оставленном релизе. Уборка не фатальна: если релиз не удалился
    (в `deploy.log` строка «не удалось удалить релиз»), выкладка всё равно кончается кодом 0. Лишний
    каталог удаляют вручную в два шага и без root, предварительно сверив, что `<id>` не равен `current`
    и `shared/state/previous`: сначала кеш от `crp` —
    `sudo -u crp find /srv/crp/releases/<id>/.next/cache -mindepth 1 -delete` (то, что не удалится,
    принадлежит `crpdeploy`), затем сам релиз — `sudo -u crpdeploy rm -rf /srv/crp/releases/<id>`. От
    root под `/srv/crp` не работать: корнем владеет `crpdeploy`, и ссылка, подложенная вместо каталога,
    увела бы удаление в чужие файлы (ops.md, риск 25). Код 1 остаётся только для сбоя health после
    переключения.

### Права на .next/cache

Каталог `.next/cache` (2770, группа crp) пишет приложение от `crp`. Подкаталоги, которые оно создаёт
с umask 022, получили бы `crp:crp 0755`, и `crpdeploy` не смог бы удалить такой релиз. Выбран
default ACL: `deploy.sh` ставит `setfacl -d -m g:crp:rwX` на `.next/cache` (нужен пакет `acl`, он в
списке шага 4 раздела 2). Новые подкаталоги получают группе crp права rwX, а `crpdeploy` входит в
группу crp. Нет `setfacl` или ФС без ACL: выкладка идёт, в журнал пишется предупреждение, а старые
релизы могут не удаляться (см. шаг 15). umask 007 для процесса в PM2 не выбран: PM2 не задаёт umask
дочернему процессу.

### Сборка не ходит в БД

На шаге 6 к релизу уже подключён `.env.production` с настоящим `DATABASE_URL`, а миграции идут
позже, на шаге 9. Production-приложение без накатанных миграций падает на проверке
`assertMigrated`. Поэтому `deploy.sh` запускает `npm run build` с подставленным недоступным
адресом БД (порт 9 на локальном интерфейсе, без пароля): значение из окружения процесса главнее
значения из `.env.production`. Если сборка попытается открыть БД, она упадёт с понятной
причиной на шаге 6, а не оставит релиз, который работает только на уже мигрированной базе.
Новый код, который читает БД при сборке (статическая генерация страниц, `generateStaticParams`
с запросом), нужно переделать, а не ослаблять эту проверку.

### Коды выхода deploy.sh

| Код | Значение | Что делать |
|---|---|---|
| 0 | выложено | ничего |
| 1 | сбой после переключения, выполнен автоматический откат | смотреть `deploy.log`; `previous` теперь указывает на сломанный релиз, не вызывайте `rollback.sh` без аргументов |
| 2 | сбой до переключения, прод не тронут | читать причину в выводе и `deploy.log`; каталог релиза удалён, журналы сборки остаются в `shared/state` |
| 4 | уже идёт другая выкладка или откат | дождаться; блокировка снимается сама |

Страницы, открытые до выкладки, при следующем переходе перезагружаются целиком
(`NEXT_DEPLOYMENT_ID`), а их файлы продолжают отдаваться из общей статики.

### Откат

```
sudo -u crpdeploy /usr/local/lib/crp/rollback.sh [--to <id релиза>] [--reason <причина>]
```

Без аргументов возвращает на `previous`, повторный вызов возвращает обратно. Около 20 секунд:
без сборки, только смена симлинка и reload. БД не откатывается.

## 5. Миграции

- Только добавляющие и идемпотентные (`IF NOT EXISTS`). Расширение закрытого списка CHECK тоже
  считается добавляющим (D-037).
- Удаление колонки или таблицы идёт в два релиза: сначала код перестаёт ею пользоваться, потом
  отдельная миграция по решению architect.
- `CREATE INDEX` на большой таблице делается с учётом `lock_timeout` (`MIGRATE_LOCK_TIMEOUT_MS`,
  по умолчанию 5000 мс).
- Миграция упала: транзакция откатилась, прод работает на старом релизе со старой схемой.
  Чиним, ставим новый тег.
- Откат кода не трогает БД: старый код работает с новой схемой, а `assertMigrated` старого релиза
  считает «лишние» миграции нормой.
- `npm run db:status` (код 0 всё накатано, 3 есть ненакатанные, 1 ошибка) показывает состояние
  без изменений. Приложение в production миграции само не накатывает.

## 6. Бэкапы и восстановление

> D-029 предложено и ждёт владельца: где вторая копия, кто хранит ключи, приемлем ли RPO 24 часа.
> Скрипты готовы, выбор владельца задаётся параметрами (раздел «Ждёт решения владельца»).

### 6.1 Что, когда и где лежит

| Что | Когда (UTC, Астана = UTC+5) | Где | Хранение |
|---|---|---|---|
| БД, `pg_dump -Fc`, шифрование age | ежедневно 21:30 (02:30) | `/var/backups/crp/daily` | 14 копий |
| то же, воскресенье по Астане | жёсткая ссылка | `weekly` | 8 копий |
| то же, первое число по Астане | жёсткая ссылка | `monthly` | 6 копий |
| Проверка восстановления | суббота 21:30 (воскресенье 02:30) | БД `crp_restorecheck`, потом удаляется | статус `verified` |
| Перед миграциями | при `db:status` с кодом 3 | `manual` | вручную, не ротируется |
| Загруженные файлы | 22:00 (03:00) | `files` (владелец crp) | 14 копий |

Каждый файл лежит рядом с `.sha256`. Разовая копия перед выкладкой (`--label`) пишет свой статус `manual-status.json` и не подменяет
статус ночного бэкапа. Статус ночного бэкапа пишется в `/var/lib/crp-ops/backup-status.json` и
`files-status.json`: `ok`, время, имя файла, размер, `verified`, `offsite`. Приватного ключа на
сервере нет. Вторая копия уходит `rsync` по SSH, если задан адрес: каждый пользователь отправляет
только свои подкаталоги (postgres: daily, weekly, monthly, manual, адрес `BACKUP_REMOTE`, ключ
`BACKUP_REMOTE_SSH_KEY`; crp: files, адрес `BACKUP_FILES_REMOTE`, ключ `BACKUP_FILES_REMOTE_SSH_KEY`).
Пустой `BACKUP_FILES_REMOTE` заменяется адресом `BACKUP_REMOTE`, а ключ запасным не бывает: без
`BACKUP_FILES_REMOTE_SSH_KEY` (или при совпадении с ключом БД) `backup.sh --files` пишет в журнал
«нужен свой ключ файлов (D-041)» и ставит `offsite=false`.

Пользователь crp читает ключ для files, поэтому взлом приложения даёт злоумышленнику запись в
хранилище файлов. Ключ бэкапа БД crp читать не должен: иначе та же уязвимость давала бы запись в
хранилище дампов. Основная защита стоит на стороне хранилища: снапшоты или неизменяемое хранилище,
которые нельзя удалить ключом бэкапа. Ограничение ключа строкой
`command="rrsync -wo -no-del -no-overwrite <каталог>",restrict` в `authorized_keys` — вторая линия:
`-wo` запрещает только чтение, удаление отключает `-no-del`, перезапись — `-no-overwrite`
(если такой опции нет в версии rrsync на хранилище, без снапшотов защиты от подмены дампов нет).

Два ключа заводятся так (на сервере и в хранилище, значения вне репозитория):

1. Ключ БД: `ssh-keygen -t ed25519 -N '' -f <файл ключа БД>`, владелец postgres, права 0600; путь в
   `BACKUP_REMOTE_SSH_KEY`. В `authorized_keys` хранилища: `command="rrsync -wo -no-del -no-overwrite <каталог БД>",restrict <открытый ключ>`.
2. Ключ файлов: то же, но файл принадлежит crp (0600, например в `/var/lib/crp/.ssh/`; ключ БД лежит в `/etc/crp`), путь в
   `BACKUP_FILES_REMOTE_SSH_KEY`, адрес с отдельным каталогом хранилища в `BACKUP_FILES_REMOTE`
   и своя строка `authorized_keys` с `rrsync` на `<каталог файлов>`.
   Сервер, настроенный по прежней версии (один общий ключ для postgres и crp): завести ключ файлов,
   сделать ключ БД `chown postgres:postgres` и `chmod 0600`, убедиться, что `sudo -u crp test -r <ключ БД>`
   возвращает ошибку, и убрать из хранилища доступ старого ключа к каталогу файлов.
   Пустой `BACKUP_FILES_REMOTE` берёт запасной `BACKUP_REMOTE`, а ключ запасного не имеет: без
   `BACKUP_FILES_REMOTE_SSH_KEY`, при совпадении с ключом БД (сравниваются настоящие пути) или если
   ключ БД читается пользователем crp, копия файлов не уходит и `offsite=false` (D-041).
3. Ключ хоста хранилища один раз добавить в `known_hosts` обоих пользователей (проверка включена,
   `StrictHostKeyChecking=yes`).
4. Проверить: `sudo -u postgres /usr/local/lib/crp/backup.sh` и `sudo -u crp /usr/local/lib/crp/backup.sh --files`,
   в статусах `offsite: true`.

Если вторая копия не уходит двое суток подряд, `healthcheck.sh` шлёт алерт `backup_offsite`. Статус
файлов учитывается, только если хранилище не пусто, адрес копии задан и статус моложе 26 часов.
Кто хранит ключи и где вторая копия, записывается вне репозитория у владельца.

### 6.2 Учебное восстановление раз в месяц (чек-лист)

1. Хранитель приносит приватный ключ age на время учения (с носителя или из менеджера паролей).
2. Взять свежий файл из `daily`; проверить сумму: `sha256sum -c <файл>.sha256`.
3. `sudo -u postgres /usr/local/lib/crp/restore.sh --file <файл> --identity <ключ>`: восстановление
   в `crp_restore_<время>`, печатаются число таблиц, последняя миграция и счётчики строк.
4. Сравнить счётчики с боевой БД (порядок величин должен совпадать).
5. Убедиться, что БД удалена (без `--keep` скрипт удаляет её сам); удалить ключ с сервера.
6. Записать дату учения в журнал учений у владельца (вне репозитория).

### 6.3 Авария: восстановление боевой БД

0. Остановить крон приложения: `mv /etc/cron.d/crp /etc/cron.d/crp.off` (mail-worker подключается
   к БД каждую минуту и мешает переименованию БД). Вернуть в конце: `mv /etc/cron.d/crp.off /etc/cron.d/crp`.
1. `sudo -u crp pm2 stop <имя из instance.json>`.
2. `sudo -u postgres /usr/local/lib/crp/restore.sh --file <файл> --identity <ключ> --target crp --force-prod`.
   Боевая БД не удаляется: она переименовывается в `crp_broken_<время>`.
3. Если код новее дампа: `deploy.sh` текущего тега не нужен, достаточно миграций:
   `cd /srv/crp/current && sudo -u crpdeploy env NODE_ENV=production node --env-file=/etc/crp/migrate.env --import tsx scripts/db-migrate.ts`.
4. Права: `sudo -u crpdeploy env NODE_ENV=production node --env-file=/etc/crp/migrate.env --import tsx scripts/db-grants.ts`
   из того же каталога (restore.sh уже выдал их по `grants.sql`; повтор безвреден).
5. `sudo -u crp pm2 start <имя>`, проверить `/api/health`.
6. Оплаты, которые прошли после времени бэкапа, восстанавливаются по банковской выписке:
   статус «Оплачено» ставится заново.
7. `crp_broken_<время>` хранить до разбора причины, затем удалить.

### 6.4 Сервер погиб

Новый сервер по разделу 2, `/etc/crp` из менеджера паролей владельца, последний бэкап из второй
копии, ключ age у хранителя, затем раздел 6.3 без шага 1.

## 7. Логи

`/var/log/crp/*.log` (PM2, крон приложения; каталог crp:adm 0750), `/var/log/crp-backup/backup.log`
(бэкап БД; каталог postgres:adm 0750, вне каталога crp, D-041) и `/var/log/nginx/crp.*`, хранение
14 дней (`deploy/logrotate/crp`). На сервере, установленном по прежней раскладке, после запуска нового
`install-ops.sh` и первой записи в новый журнал старый каталог `/var/log/crp/backup/` удалить:
`rm -r /var/log/crp/backup`. Если `install-ops.sh` предупредил, что `/var/lib/crp-ops/backup-status.json` или
`manual-status.json` занят каталогом или ссылкой, удалите их от root (`rm -r`) и запустите установку снова;
`backup.sh` пишет в журнал «не удалось записать статус», когда такое имя занято. В журнале доступа nginx нет
query string и Referer: там бывают ключи заказов и токены. Журнал ошибок nginx ведётся с уровня
crit, потому что записи уровня error содержат строку запроса. Журнал Postgres не пишет значения
параметров запросов (`log_parameter_max_length = 0`). Крон-скрипты пишут только счётчики и id. **Логи с прода не вставлять в ИИ-сессии**
(AGENTS.md): для разбора только обезличенная выдержка.

## 8. Мониторинг

`healthcheck.sh` раз в 5 минут, состояние в `/var/lib/crp-ops/monitor-state.json`. Алерт уходит
только при смене состояния. В тексте алерта: имя проверки, имя экземпляра и время, без IP и ПДн.

| Проверка | Порог | Что делать при алерте |
|---|---|---|
| `app_health` | `/api/health` не `ok` или медленнее 5 с | раздел 11: 502, `migrations=pending` |
| `pm2` | процесс не `online`; warn при +3 рестартах за час | `pm2 logs`, раздел 11: цикл рестартов |
| `backup`, `backup_files` | статус не `ok` или старше 26 часов | `/var/log/crp-backup/backup.log` (БД), `/var/log/crp/backup-files.log` (файлы); чаще всего заглушки вместо ключей age или нет места |
| `backup_offsite` | `offsite=false` при заданном `BACKUP_REMOTE` (дампы БД) или `BACKUP_FILES_REMOTE`/`BACKUP_REMOTE` (файлы): warn, через 48 часов подряд fail | доступность хранилища, ключ SSH и ключ хоста, `backup.log`; файлы учитываются при непустом хранилище и статусе моложе 26 часов |
| `disk` | меньше 20 % warn, меньше 10 % fail | раздел 11: диск |
| `tls_cert` | меньше 21 дня warn, меньше 7 fail | раздел 11: сертификат |
| `external` | `https://<домен>/api/health` недоступен | DNS, TLS, nginx |

Внешний uptime-монитор по умолчанию не подключён (решение владельца). Он видел бы только
`/api/health`, без ПДн.

### Крон

`/etc/cron.d/crp` (из `deploy/cron/crp.cron`). Время сервера UTC, часовой пояс в cron не
задаётся: на Ubuntu он работает ненадёжно. Приложение запускается только через
`run-script.sh`: `flock` (без наложений; занятый запуск пропускается с кодом 0) и `timeout 15m`.

| Задача | Расписание (UTC) | По Астане |
|---|---|---|
| `mail-worker` (очередь писем) | каждую минуту | каждую минуту |
| `send-reminders` | `0 4-14 * * *` | ежечасно с 09:00 до 19:00 |
| `files-sweep` | 23:00 | 04:00; флаг `UPLOADS` не проверяется: мусор убирается всегда |
| `backup.sh` | 21:30, суббота с `--verify-restore` | 02:30 |
| `backup.sh --files` | 22:00 | 03:00 |
| `healthcheck.sh` | каждые 5 минут | |

Скрипт, которого нет в текущем релизе, пропускается («нет в этом релизе»). Флаги функций
(`REMINDERS` и др.) проверяет сам скрипт.

## 9. Секреты

Список хранится у владельца, в репозитории только имена переменных.

- `SESSION_SECRET`: смена выкидывает всех пользователей из системы.
- `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`: один для всех релизов; смена ломает открытые формы.
- Пароли `crp_app` и `crp_owner`: `\password` в psql, правка `app.env` или `migrate.env`,
  `pm2 reload`.
- Ключ age: старые бэкапы не перешифровываются, новые идут на новые открытые ключи; старый
  приватный ключ хранится до истечения ротации.
- Токен бота алертов: только в `/etc/crp` и у владельца. Ключ SSH для дампов БД: в `/etc/crp`, владелец
  postgres, 0600. Ключ для файлов принадлежит crp (0600, путь в `BACKUP_FILES_REMOTE_SSH_KEY`); он
  по построению доступен приложению, поэтому хранилище файлов отдельное и только на запись.

## 10. Стейдж и приёмка (условие «готово» из #24)

Стейдж ставится на отдельном сервере (или виртуальной машине) по разделу 2 с собственным
доменом под basic auth, только синтетические данные. На одном сервере с продом комплект его не
поддерживает: `install-ops.sh` пишет сайт nginx, крон и скрипты в общие пути (`crp.conf`,
`/etc/cron.d/crp`, `/usr/local/lib/crp`), и запуск для стейджа заменил бы настройки прода.

- [ ] Установка с нуля по разделу 2, без шагов, которых нет в документе.
- [ ] `deploy.sh vA`, `create-admin`, вход, создание курса.
- [ ] Под нагрузкой (два терминала: `while :; do curl -s -o /dev/null -w '%{http_code}\n' https://<стейдж>/ru; done | sort | uniq -c`)
      выполнить `deploy.sh vB` с новой миграцией: ноль ответов 5xx, `/api/health` показывает vB,
      вкладка, открытая до выкладки, после перехода перезагружается и работает.
- [ ] `rollback.sh`: vA работает с новой схемой, ноль 5xx.
- [ ] Сломанный релиз (тег с падающей сборкой или проверкой): код 2, прод не тронут; релиз,
      падающий после переключения: автооткат, код 1.
- [ ] Сборка без доступа к БД проходит (раздел 4); `npm run build` с рабочим `DATABASE_URL`
      ведёт себя так же.
- [ ] `backup.sh --verify-restore`: статус ok; `restore.sh` с настоящим ключом в
      `<стейдж>_restore_*`: счётчики совпадают.
- [ ] Перезагрузка сервера: PM2 поднимает приложение, health ok.
- [ ] `certbot renew --dry-run` проходит.
- [ ] Остановить приложение: `healthcheck.sh` фиксирует fail, после старта ok; алерт пришёл ровно два раза.
- [ ] Статика через nginx: `curl -I https://<стейдж>/_next/static/<файл из .next/static>` отвечает 200
      (права общей статики o+r, каталоги o+x), страница открывается со стилями.
- [ ] Картинка урока с внешнего https-адреса не показывается: CSP `img-src 'self'` это блокирует
      намеренно (D-009, адрес читателя не уходит внешнему хосту). Авторам: картинки только из
      загрузок платформы.
- [ ] Нет заголовка `X-Powered-By`, есть CSP и HSTS; в консоли браузера нет нарушений CSP на
      страницах каталога, урока с YouTube, теста, сертификата, админки.
- [ ] Подделка IP: `curl -H 'X-Forwarded-For: 203.0.113.7' ...`, лимит входа считается по
      реальному IP (21-я неверная попытка с одного IP блокируется).
- [ ] Крон: `mail-worker` раз в минуту, `send-reminders` с 04:00 до 14:00 UTC, `files-sweep`
      в 23:00 UTC; в `/var/log/crp` видны запуски и коды.

## 11. Инциденты

- **502 и страница обслуживания.** Процесс упал: `sudo -u crp pm2 status`, `pm2 logs`. Если рядом
  выкладка, посмотреть `deploy.log` и при необходимости `rollback.sh`.
- **health=fail, `migrations=pending`.** Выложили без миграций или откатились на код, которому
  нужна схема новее файла: выполнить миграции из `current` (раздел 6.3, шаг 3).
- **Диск заполнен.** Сначала `releases/` и `/var/log/crp`, затем старые копии в `manual`
  (чистятся вручную). Бэкапы и данные не удалять без второй копии.
- **Postgres не стартует.** `journalctl -u postgresql`, свободное место, права на каталог данных;
  каталог данных не удалять и не пересоздавать, пока не снята копия.
- **Истёк сертификат.** `certbot renew`, `systemctl reload nginx`; причина: таймер или webroot.
- **Цикл рестартов.** `max_memory_restart` 1200 МБ и `max_restarts` 10: смотреть `*-err.log`,
  выкладка последнего релиза, нехватка памяти; откат `rollback.sh`.
- **Автооткат не удался.** Приложение недоступно, `deploy.sh` вернул 1 и написал об этом:
  `rollback.sh --to <id>` с известным рабочим релизом из `releases/`.

## 12. Нельзя

- Подменять `.next` на месте и править файлы в `releases/` руками.
- `pm2 restart` вместо `startOrReload` (даёт 502 на время перезапуска).
- `DEMO_MODE`, `SEED_DEMO`, `PGLITE_DIR` на проде.
- Копия бэкапа за пределами РК.
- ПДн и логи с прода в ИИ-сессиях.
- IP, пароли, ключи и содержимое `/etc/crp` в репозитории, issue и PR.
- Убирать или ослаблять CSP у `/api/files/`: nginx добавляет общий заголовок поверх
  заголовка приложения, браузер применяет оба.
- Ослаблять проверку «сборка не ходит в БД».
