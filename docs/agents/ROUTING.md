# Оркестратор и маршрутизация моделей

Цель — тратить лимиты старших моделей только там, где они дают качество, а
всю рутину отдавать младшим, **не теряя качества результата**.

## Схема

```
Владелец (задача / issue)
        │
        ▼
Оркестратор = главная сессия (Opus)
  • понимает задачу, режет на подзадачи, присваивает уровень T0/T1/T2
  • раздаёт подзадачи подагентам, сам код почти не пишет
  • собирает результат, проверяет, коммитит, пушит, ведёт PR
        │
        ├── T0 · Haiku  ── scout, Explore (поиск, чтение), mechanic (механические правки)
        ├── T1 · Sonnet ── builder (реализация по ТЗ), tester (проверки и тесты)
        └── T2 · Opus   ── architect (решения с высокой ценой ошибки), reviewer (ревью перед пушем)
```

Подагенты лежат в `.claude/agents/`, модель зашита в их frontmatter (`model:`),
поэтому выбор модели не зависит от памяти оркестратора. Проектный
`.claude/settings.json` ставит `CLAUDE_CODE_SUBAGENT_MODEL=sonnet`: любой
подагент без явной модели (general-purpose, агенты workflow) идёт на Sonnet, а
не наследует Opus.

## Как выбрать уровень

| Уровень | Модель | Подагенты | Когда | Примеры в этом проекте |
|---|---|---|---|---|
| **T0** | Haiku, effort low | `scout`, `Explore`, `mechanic` | Ответ однозначен, суждение не нужно. Ошибку видно сразу и она дешёвая. | Найти, где проверяется доступ к уроку. Пересказать лог CI. Переименовать компонент. Добавить ключи локализации по готовому списку. Обновить таблицу в docs по известным фактам. |
| **T1** | Sonnet, effort medium | `builder`, `tester` | Понятное ТЗ, один модуль, есть образец в коде. Ошибку ловят тесты и ревью. | Страница каталога курсов. CRUD уроков в админке по схеме. Квиз по описанной логике. Экспорт прогресса в CSV. Починить тест с известной причиной. |
| **T2** | Opus, effort high | `architect`, `reviewer` | Цена ошибки высокая или требования неясны. Решение трудно откатить. | Схема БД и миграции. Оплата, вебхуки, возвраты. Выдача и отзыв доступа. Роли и компании-клиенты. Безопасность загрузки файлов. Ревью перед мержем. Баг, который T1 не победил. |

Быстрый тест для оркестратора — три вопроса:
1. **Нужно ли выбирать между вариантами решения?** Нет → T0. Да → дальше.
2. **Есть ли готовое ТЗ и образец в коде, а ошибку поймают тесты?** Да → T1.
3. **Затрагивает деньги, доступы, ПДн, схему БД или неясно, как делать?** Да → T2.

## Правила качества (без них экономия запрещена)

1. **Ревью не экономим.** Любой дифф с кодом перед пушем проходит `reviewer`
   (Opus). Для чисто документационных диффов — достаточно самопроверки оркестратора.
2. **Деньги и доступы — только T2** на этапе проектирования и ревью.
   Реализацию по утверждённому дизайну может делать `builder`.
3. **Эскалация вверх, не повтор.** T0 отказался или T1 дважды не справился —
   переводим задачу на уровень выше с описанием, что пробовали. Не гоняем
   ту же модель третий раз.
4. **Проверяемость.** Результат T0/T1 принимается, только если его можно проверить:
   тесты, typecheck, lint, сверка с ТЗ. Нечем проверить — уровень выше.
5. **Контекст режем, а не копируем.** В промпт подагенту — цель, пути к файлам,
   критерий готовности. Не вставлять целые файлы и логи: подагент прочитает сам.
6. **Параллелим независимое.** Несколько T0/T1 задач без общих файлов —
   запускать одновременно (в одном сообщении). Правки одних и тех же файлов —
   последовательно или в отдельных worktree.

## Шаблон поручения подагенту

```
Цель: <одно предложение, что должно получиться>
Контекст: <issue #N, раздел SPEC, ключевые пути>
Границы: <какие папки можно менять, что нельзя трогать>
Готово, когда: <проверяемый критерий: тест X зелёный / страница Y открывается / …>
Верни: <список файлов + краткий итог / найденные факты / вопрос на эскалацию>
```

## Метки в GitHub

У каждой задачи есть метка уровня. По ней оркестратор (или человек) сразу
видит, кому её отдавать:

- `tier:T0` — Haiku: поиск, механика, документация по фактам.
- `tier:T1` — Sonnet: реализация по ТЗ, тесты.
- `tier:T2` — Opus: архитектура, деньги, доступы, безопасность, ревью.

Метку ставит тот, кто заводит задачу, по таблице выше. Сомневаешься — ставь
уровень выше.

## Workflow-скрипты

В скриптах Workflow модель задаётся на каждый вызов:
`agent(prompt, { model: 'haiku' | 'sonnet' | 'opus', effort: 'low' | 'medium' | 'high' })`.
Правило то же: сбор и поиск — `haiku`, реализация — `sonnet`, проверка и судья —
`opus`. Если модель не указана, срабатывает `CLAUDE_CODE_SUBAGENT_MODEL` (Sonnet).

## Если нужно ещё экономнее

- Главную сессию можно запускать с `/model opusplan`: Opus в режиме плана,
  Sonnet при исполнении. Подходит для задач, где план важнее кода.
- `/effort` у главной сессии снижать на рутинных днях (правки текстов, мелкие баги).
